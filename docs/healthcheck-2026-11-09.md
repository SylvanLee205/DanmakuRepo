## 二、bug 1：`onTaskError` 失败不写库（最严重）

### 现象
状态库里 2 条 `dm_video` 永远停在 `rendering`、`attempts=0`、`last_error=None`：

```
2026-11-06 18:54:48  seg=4  君君.-2026年11月06日18点52分（弹幕版）.mp4
2026-11-07 15:19:11  seg=1  vvu-2026年11月07日14点19分（弹幕版）.mp4
```

但日志里这两段**明确失败过**：
```
[11-06 18:55:09] render/error 渲染产物时长异常：源 134 秒 → 产物 95 秒（71%）
[11-07 15:21:19] render/error 渲染产物时长异常：弹幕 3589 秒 → 产物 3096 秒（86%）
```
两处都跟着一行 `dm_video 标记为 failed（任务失败，不再等待）`。

### 排查
1. 全库 `state='failed'` 计数 = **0**（`src_video` 和 `dm_video` 都是）→
   说明 `_STATUS_TO_STATE['failed']` 这条映射**从未真正生效**。
2. 那条映射是 10-19 补的，注释写着"之前没有这个映射 → 状态写不进库"——
   但补了映射之后仍然不生效，因为**没人去调同步函数**。
3. 逐个核查 `liveevents.py` 里全部 `['status'] = '...'` 赋值点（11 处）：
   其他 10 处后面都紧跟 `_sync_artifact(...)`，**只有 `onTaskError` 里那处没有**。

### 真因
`onTaskError` 只改了内存 `state_dict`，没有做持久化镜像。10-05 那次修复解决的是
"内存状态不收敛"（清理防线永远挡着），但**没解决"状态不落库"**。

### 为什么后果比想象中重
进程连续跑 6 天不重启，`reconciler._step0_sanitize_unstable`（启动时把
`rendering`/`uploading` 降级）**一次都没跑过**，所以卡住的记录一直卡着：

```
渲染失败 → 内存标 failed（本次运行内正确，清理能继续）
         → 库里仍是 rendering
         → 下次重启：降成 recorded → 重新渲染 → 又失败
         → 无限循环，且 attempts 永远是 0（看不出反复失败）
```

### 修法
- `onTaskError` 收集被标 failed 的槽位，循环结束后统一调 `_persist_failed()`
- `_persist_failed()` 写 `FAILED` + `last_error`（错误描述切 500 字）+ `attempts+1`
- 为什么不用现成的 `_sync_artifact(state=FAILED)`：它走
  `set_artifact_state(key, state)` 时不带 `last_error`，库里只剩个干巴巴的
  failed，下次重跑还是原地踩坑。所以直接调 repository 把三者一起写。
- 整个方法**不抛异常**：状态写库失败绝不能连累清理判定，否则回到 10-05
  那个"源视频永不清理"的老问题。

### 验证
- `unit_tests/test_liveevents_state.py` 新增 5 个用例：
  - 失败后库里必须是 FAILED（不是 RENDERING）
  - `last_error` 必须含错误原因
  - `attempts` 要累加到 2
  - 状态库炸了不能让清理判定跟着崩
  - 没注入状态库时是 no-op（纯运行时模式）
- **反向验证**：把落库调用注释掉 → 3 个用例立刻失败，报错正是预期文案。
- 历史数据：`tools/fix_stuck_artifacts.py --apply` 把 2 条按磁盘事实改成
  `recorded`（成品确实不在 → 回 recorded 等重新渲染）。已备份 .db。

## 三、bug 2：`clean_sources.py` 只认老布局

### 现象
跑它报"没有可清理的文件"，但磁盘上明明堆着 11-02~11-03 的老源视频。

### 真因
它的目录模型是**改版前**的：
```
老：直播回放/<主播>/            原视频
    直播回放/<主播>（弹幕版）/  成品
```
11-02 改成：
```
新：直播回放/原视频/<主播>/
    直播回放/弹幕版/<主播>/
```
于是 `os.listdir('直播回放')` 只看到 `原视频` 和 `弹幕版` 两个容器，把它俩当主播名
去找 `原视频（弹幕版）`，永远找不到 → 整个工具静默退化成空操作。

### 波及
`掉了颗兔牙-2026年11月03日00点20分(2).ts`（755MB）还有第二层原因：
成品叫 `...(2)（弹幕版）.mp4`，而判据是 `stem + （弹幕版）.mp4` 精确匹配，
差一个 `(2)` 就永远对不上。4 个已上传分段的源视频（2.2GB）因此躺了一周。

### 修法
- `_scan_layouts()`：同时返回新布局（两级）和老布局（单级），互不冲突
- `_exists_rendered()`：容忍 `(1)`~`(9)` 重名后缀，外加前缀 + `(\d+)` 的正则兜底

## 四、bug 3：云端校验用截断前缀 → 会误删

### 现象（修 bug 2 之后立刻暴露）
清单从"空"变成 **79 个 / 44.5GB**，其中包含：
```
698.9 MB  [云端已有]  vvu-2026年11月07日14点19分.ts
 27.8 MB  [云端已有]  君君.-2026年11月06日18点52分.ts
```
而这两段**恰恰就是 bug 1 里渲染失败、从未上传的那两段**。

### 真因
```python
cloud_hit = any(n.startswith(stem[:max(1, len(stem) - 6)]) for n in cloud_set)
```
截掉末 6 个字符（那是照 `14点19分` 的长度猜的），把时间戳削成 `...11月07日`：
```
源    vvu-2026年11月07日14点19分
截断  vvu-2026年11月07日
命中  vvu-2026年11月07日15点19分（弹幕版）.mp4   ← 同一天另一场
```
只要那天**任意**一场录制上了云，任何分段都会被判成"云端已有"。

### 修法
`_exists_in_cloud()` 改成严格同名：云端名必须是 `<stem>（弹幕版）.mp4` 或
`<stem>(n)（弹幕版）.mp4`，**绝不截断 stem**。并加静态断言禁止再出现
`stem[:len(stem)-N]` 这种写法。

## 五、bug 4：完全无视 24h 延迟清理队列

### 险情
修完前两个 bug，工具列出 79 个候选（44.5GB）。但对比 `pending_clean.json` 才发现：

```
候选 79 个
  仍在 24h 延迟清理队列里：66 个 / 40.92 GB   ← 刚渲染完，还没上传
  不在队列里：            13 个 /  3.62 GB   ← 真僵尸
```

工具的判据只是"本地有渲染产物"，但 DMR 的正式流程是
**渲染 → 上传 → 进队列等 24 小时 → 才删**。"已渲染"和"已上传"是两个完全不同的
阶段。谁顺手 `--apply`，就把刚渲染完没上传的全删了，还绕过了保护窗口。

### 修法
`_pending_clean_names()` 读队列里的文件名集合，命中即跳过（原因写
"在 24 小时延迟清理队列中"）。**队列读不出来时按"全部保护"处理** ——
宁可不清，不可错清。

> **⚠️ 2026-11-09 补记（用户提醒后修正）**：上表「已上传」是**这 5 条的
> 实际情况，不是删除的通用前提**。项目有「跳过上传」机制
> （`render_args.dmrender.skip_upload_rule`）：横屏是必选前提，码率 ≥2500kbps
> 或帧率 ≥40fps 再命中任意一个 —— 也就是**三条里命中两条就整组不上传**
> （B站和网盘都不传）。配置里 `skip_min_matches: 1` 看着像「命中一条」，
> 是因为横屏被排除在计数外，实际语义就是「横屏 + 一个数值条件」。
>
> `configs/global.yml` 原文：**「跳过上传不影响本地文件：原视频照常按
> clean_args 删除，弹幕版按 clean_args 留存（不上传也不删）」**。
> 所以命中规则的分段**云端永远查不到，但源视频本来就该删**。把「云端有」
> 当硬门槛，会让这批源视频永久滞留。
>
> 复核结论：**本次没有误删**。库里 21 条 `dm_video: skipped` 全是 11-05
> 之后的断尾的人类不会喵 / 怦怦！ / 小鱼大王，与上表 11-02~11-03 的
> 5 条完全不重合；且这 21 条中 18 条的源视频已按 24h 队列清掉、3 条
> 仍在队列，链路正常。`掉了颗兔牙(2)` 那条日志写的是「读不出时长、
> 渲染产物缺索引」→ 属于**渲染残缺**跳过上传，不是命中规则；同场第一版
> 3601 秒完整成品已上云，删源不丢内容。

`掉了颗兔牙` 这条特别查了一下：本地有两个成品 ——
`（弹幕版）.mp4`（3601 秒，已上传、云端有）和 `(2)（弹幕版）.mp4`
（2995 秒，日志判定"读不出时长、跳过上传"）。后者的**内容**已经通过前一版
上云了，所以删源文件不会丢内容。

清理后：`原视频` 41 → 36 个 .ts，`弹幕版` 173 个 mp4 不变，再跑工具报"无残留"。
